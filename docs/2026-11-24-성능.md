# 폰 성능 (11/24 밤)

메인 실시간 배치에서 스테이지 4(적 상한 85)가 fps 37로 떨어진 일을 폰 기준으로 다시 쟀다.

## 재는 법: tools/perf.ts

```
npm run build:web
node tools/perf.ts [--scenes auto-cue-s4,auto-olly-s14,auto-pale-s15] [--throttle 4] [--seconds 20] [--warm 15] [--profile --html <압축 안 한 빌드>]
node tools/build-web-dev.mjs <파일>   # 압축 안 한 빌드 (프로파일에서 함수 이름이 보이게)
```

- Pixel 7(412×915, 배율 2.625) + CDP `Emulation.setCPUThrottlingRate` 4. 시험 진입로 자동 플레이(`#auto-<캐릭터>-s<스테이지>-x1`, 봇 빌드로 시작)를 실시간으로.
- 게임 안 계측 `window.__pop.perf` (web/main.ts): 프레임마다 sim(시뮬 틱 step+이벤트), draw(월드 그리기 drawWorld), hud(DOM), 프레임 간격.
- 헤드리스 크롬은 캔버스를 소프트웨어로 그린다. 실제 폰(GPU)과 절대값은 다르니 전후 비교용.

## 찾은 것: 병목은 코드가 아니라 캔버스 픽셀 수

| 스테이지 14 올리 (CPU ×4) | fps | 프레임당 JS (sim+draw+hud) |
|---|---|---|
| 그대로 (그리기 해상도 2, 캔버스 약 824×1830) | 23 | 4.1ms |
| 기기 배율 1로 연 것 | 56 | 2.5ms |
| 같은 기기, 캔버스 해상도만 1.5 | 41 | 2.8ms |
| 1.25 | 49 | 2.7ms |
| 1 | 58 | 2.1ms |

- 우리 JS는 프레임당 3~4ms뿐인데 간격은 33~50ms. CPU 프로파일의 89%가 "(program)" = 브라우저의 캔버스 그리기(래스터)·합성.
- 화면이 똑같은 코드 손질(바깥 어둠 전체 칠하기 → 울타리 밖 띠만, 화면 밖 적 안 그림, matchMedia를 매 프레임 만들지 않음, 불투명 캔버스)은 측정 잡음 안이었다 (넣어 두었다: 해가 없고 조금은 준다).

## 고친 것: 느린 기기에서만 그리기 해상도를 낮춘다

- 판 중 프레임 간격 중앙값(60프레임)이 20ms(50fps 아래)를 넘으면 해상도를 0.25씩 낮춘다 (최저 1). 한 번 느렸던 해상도로는 다시 올리지 않는다 → 오르내리지 않고 자리 잡는다. 충분히 빠르면(중앙값 17.5ms 이하가 4번) 느렸던 적 없는 해상도로만 올린다.
- 자리 잡은 값은 기기에 기억해(localStorage) 다음에 열 때 처음부터 그 값으로 (처음 몇 초 끊김 없음).
- **빠른 기기는 해상도 2 그대로** (감속 없이 재면 해상도 2, 60fps) → 화면이 전과 같다. 느린 기기에서는 캔버스가 조금 부드러워진다(HUD·버튼은 DOM이라 그대로 선명).
- 시뮬은 건드리지 않았다 (src 변경 없음, 330 테스트 통과). 웹의 `g.view`(보이는 월드 크기)는 캔버스 가로세로 비율로 정해져 해상도와 무관하다.

## 남은 것

- p95가 33ms(가끔 한 프레임 건너뜀)는 남는다. 다음 후보: 풀밭 바둑판을 오프스크린 캔버스에 한 번 그려 두고 복사, HUD DOM을 10Hz마다 통째로 다시 만드는 것 대신 글자만 바꾸기.
- 실제 폰(GPU 래스터)에서는 해상도 2로도 버틸 수 있다. 그런 기기는 자동으로 2에 남는다.
